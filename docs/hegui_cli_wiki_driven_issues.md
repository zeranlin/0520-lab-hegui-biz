# hegui_cli.py Wiki 驱动与反馈机制记录

记录时间：2026-05-14

## 定位

`hegui_cli.py` 是政府采购招标文件合规性审查生产线的执行器，不是审查知识库。

biz 侧只负责两类事情：

1. 有效被 `lab-hegui-llm` 驱动。
2. 提供生产线工程能力。

当 `lab-hegui-llm` 的知识或协议无法有效驱动审查时，biz 侧只能记录和反馈问题，不能在执行器内写死业务审查知识。

## 职责边界

### 1. Wiki 驱动执行

执行器应当：

- 接收一个待审文件。
- 读取 `config/hegui.yaml` 指向的只读 LLM Wiki。
- 按 LLM Wiki 入口指引执行：文件画像、知识路由、动作清单、逐动作执行、风险原子化、质量门、报告。
- 记录每个阶段调用的 Wiki 页面。
- 保留动作 ID、风险审查点、原文证据和中间产物的反链。
- 在运行记录中说明外部标注、历史答案、Wiki 修改和 Wiki 维护命令均未使用。

执行器不得：

- 在 biz 侧沉淀政府采购业务审查知识。
- 用代码规则替代 LLM Wiki 的审查协议。
- 修改、维护、lint、ingest 或 query LLM Wiki。
- 因性能优化牺牲政府采购招标文件审查的关键覆盖面。

### 2. 工程生产能力

biz 侧可以并且应当维护：

- LLM 服务配置读取和鉴权。
- 大文件分段和上下文预算。
- 输出目录按秒隔离，避免覆盖历史产物。
- 中间产物完整落盘。
- Windows/macOS 路径和编码兼容。
- PDF、DOCX、TXT 等文件抽取能力。
- 模型返回用量、prompt hash、output hash、重试记录。
- 上下文超限、模型服务错误、协议校验失败的可解释报错。

这些能力属于生产线工程能力，不属于业务审查知识。

## Wiki 驱动不足反馈机制

当出现以下情况时，应形成反馈记录：

- LLM Wiki 没有给出足够明确的可执行协议。
- 模型输出的风险无法反链到 Wiki 审查点或动作。
- 质量门无法判断某类风险是否漏报或误报。
- 文档抽取质量影响模型判断，但 Wiki 协议没有要求如何处理不确定性。
- 多次运行对同一高价值风险输出不稳定。

反馈记录应包含：

| 字段 | 说明 |
| --- | --- |
| 触发案例 | 待审文件和输出目录 |
| 问题现象 | 报告或中间产物中的具体错误 |
| 链路定位 | 错误最早出现在哪个阶段 |
| Wiki 已有依据 | 当前调用到的 Wiki 页面和已有要求 |
| 缺失协议 | Wiki 还缺少什么可执行要求 |
| biz 可做事项 | 只限工程能力，不写业务判断 |
| 建议处理 | 建议由 LLM Wiki 补充的知识或协议 |

## 反馈记录 1：评分办法分值复核误判

### 触发案例

- 待审文件：`raw/四川文件/第一次 测试丹巴县2024年中央财政林业草原专项资金造林绿化项目.pdf`
- 输出目录：`outputs/四川文件/2026-05-14_09-05-51`

### 问题现象

报告输出：

> 评分办法分值总和仅为89分，缺失11分，导致评审标准不完整。

经复核，普通 PDF 抽取文本中评分表列关系被打散，模型漏读了价格分 `30.00`，把价格分误识别为 `10分`。

使用版式视图复核，评分表中可识别的分值包括：

| 评审项 | 分值 |
| --- | ---: |
| 技术指标和配置 | 10 |
| 实施方案 | 30 |
| 保障方案 | 15 |
| 后续服务 | 15 |
| 价格分 | 30 |
| 利润率 | 10 |
| 履约能力 | 7 |
| 财务报告 | 2 |

因此，“89分、缺失11分”是错误结论。更合适的审查口径应是：评分分值口径或归属存在异常，需逐项复核，不应直接断言缺失 11 分。

### 链路定位

错误最早出现在 `01-文件画像`：

- 画像中已将价格分写成 `10分`。
- `04-动作执行记录` 继续沿用该错误，形成 `10 + 60 + 19 = 89` 的候选风险。
- `05-原子风险清单` 和最终报告将该错误固化为确定风险。

这说明问题不是报告阶段偶发，而是早期画像和动作执行阶段对评分表结构理解错误。

### Wiki 已有依据

当前已调用或相关 Wiki 页面包括：

- `wiki/20-知识点/评分办法审查.md`
- `wiki/20-知识点/政府采购逐章审查矩阵.md`
- `wiki/25-风险审查点/评审因素与采购需求脱节.md`
- `wiki/25-风险审查点/价格分和报价规则异常.md`

这些页面已经要求审查评分因素、价格分、技术分、商务分和分值权重，但尚未明确评分表分值复核的可执行动作。

### 缺失协议

建议 LLM Wiki 补充“评分办法分值复核动作协议”，至少明确：

- 必须逐项列出评分项、分值、原文位置。
- 必须展示合计公式。
- 必须区分“确定错误”和“表格抽取/分值归属待复核”。
- 对 PDF 表格错位、分值归属不清、一级/二级评审项混排等情况，不得直接输出“缺少多少分”的确定结论。
- 质量门必须反查评分分值风险是否具备逐项明细和合计过程。

### biz 可做事项

biz 侧可以提供工程支持：

- 保留原始抽取文本。
- 后续可增加版式抽取视图或表格视图，作为模型输入材料。
- 在运行记录中标记抽取方式和上下文规模。
- 当模型输出评分分值确定性结论但缺少逐项明细时，可作为协议不足反馈记录。

biz 侧不应写死评分表计算规则，也不应在执行器里内置政府采购评分风险判断。

### 建议处理

本问题应反馈给 `lab-hegui-llm`：由 Wiki 增加评分办法分值复核协议和质量门要求。`hegui_cli.py` 保持薄执行器，只负责按协议执行和记录反馈。

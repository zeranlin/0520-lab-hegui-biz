# hegui_cli.py 审查 SOP

记录时间：2026-05-14

## 1. 目标

本 SOP 用于审查 `hegui_cli.py` 是否仍然符合政府采购招标文件合规性审查生产线定位。

审查结论只回答四个问题：

1. 是否有效被 `lab-hegui-llm` 驱动。
2. 是否越界写入了 biz 侧业务审查知识。
3. 是否具备稳定生产线工程能力。
4. 当 Wiki 无法有效驱动时，是否形成了反馈，而不是在 biz 侧补业务规则。

## 2. 基本原则

`hegui_cli.py` 是执行器，不是知识库。

允许做：

- 接收一个待审文件。
- 读取只读 LLM Wiki。
- 按 Wiki 入口指引执行审查流水线。
- 调用小模型。
- 处理大文件、上下文、重试、输出目录、运行记录和跨平台兼容。
- 在 Wiki 驱动不足时记录反馈。

不允许做：

- 在代码中写死政府采购风险判断。
- 在代码中写死品类、地域、评分、合同、资格等业务规则。
- 用执行器规则替代 Wiki 审查协议。
- 修改、lint、ingest、query 或反哺 `lab-hegui-llm`。
- 使用标准答案、外部标注或历史审查记录反推风险。

## 3. 审查准备

审查前先确认：

- 当前待审代码范围。
- `lab-hegui-llm` 只读。
- `outputs/`、`raw/`、配置密钥不纳入提交。
- 如涉及回归运行，使用新的按秒输出目录，不覆盖历史结果。

建议先执行：

```bash
git status --short
python3 -m py_compile agents/hegui-agent/hegui_cli.py
python3 agents/hegui-agent/hegui_cli.py --help
```

## 4. Wiki 驱动审查

### 4.1 入口指引

检查点：

- 是否读取 `config/hegui.yaml` 中的 `wiki_home`。
- 是否读取 LLM Wiki 入口指引。
- 是否按入口指引执行固定流水线。
- 是否在运行记录中列出调用知识页。

通过标准：

- 代码只负责调度。
- 风险判断来自 Wiki 知识和待审文件原文。
- 运行记录能说明本次使用了哪些 Wiki 页面。

失败信号：

- 代码中出现业务判断常量、硬编码风险标题、硬编码品类风险清单。
- 模型 prompt 中出现 biz 自造审查规则，而非引用 Wiki。

### 4.2 流水线完整性

必须覆盖：

1. 文件画像。
2. 知识路由。
3. 动作清单。
4. 逐动作执行。
5. 风险原子化。
6. 质量门反查。
7. 报告生成。
8. 运行记录。

审查方法：

- 检查代码阶段是否完整。
- 检查每个阶段是否落盘。
- 检查报告风险是否能反链到动作 ID、审查点、原文位置。

失败信号：

- 某阶段只存在内存中，没有中间产物。
- 报告直接从原文生成，绕过动作、原子化或质量门。
- 风险没有关联动作 ID 或审查点。

## 5. biz 越界审查

### 5.1 业务知识硬编码

重点搜索：

```bash
rg -n "物业管理|家具|医院|评分|资格|合同|风险|审查点|动作ID|PROP-|FURN-|GEN-|通用矩阵" agents/hegui-agent/hegui_cli.py
```

判断标准：

- 如果这些内容用于读取 Wiki、路径名、产物名称，可以接受。
- 如果这些内容用于判断风险、生成风险、强制业务动作，不接受。

### 5.2 工程能力和业务知识区分

允许：

- PDF/DOCX/TXT 抽取。
- 结构化表格可读性增强，例如保留 PDF 版式、DOCX 表格行列边界。
- 通用算术自洽校验，例如模型输出的多项数字合计与声明合计不一致时要求重试或标记待复核。
- 大文件分段。
- prompt token 预算。
- 模型超时和重试。
- 运行记录和 hash。
- 输出目录隔离。

不允许：

- 代码里判断某评分项是否违法。
- 代码里判断某合同类型是否错配。
- 代码里判断某证书是否与项目无关。
- 代码里写死某品类应执行哪些审查动作。
- 代码里用固定业务分值结构替代 Wiki 协议或待审文件原文。

## 6. 大文件与性能审查

检查点：

- 是否有上下文预算。
- 是否大文件分段读取。
- 分段合并是否保留原文行号和证据。
- 是否记录每阶段 prompt tokens、completion tokens、total tokens。
- 是否记录 prompt hash 和 output hash。
- 是否对上下文超限给出明确错误或降级策略。

通过标准：

- 性能优化不删除 Wiki 要求的必读章节。
- 压缩或分段不会让评分办法、资格/符合性、采购需求、合同、履约验收等核心章节消失。
- 运行记录可复查每阶段规模和是否触达输出上限。

失败信号：

- 为了加速直接删除核心章节。
- 只保留摘要，后续质量门无法回查完整证据。
- 模型输出触达上限仍被当作可信结果。

## 7. Wiki 驱动不足反馈

当出现以下情况，不应直接在 biz 修业务规则：

- 同一文件多次运行，高价值风险不稳定。
- 模型输出明显误判，但 Wiki 没有给出可执行反查协议。
- 报告风险无法反链到动作和审查点。
- 文档抽取造成不确定性，而 Wiki 没规定不确定时如何输出。
- 质量门无法识别某类误报或漏报。

应形成反馈记录，包含：

| 字段 | 内容 |
| --- | --- |
| 触发案例 | 待审文件、输出目录 |
| 问题现象 | 具体错误报告或中间产物 |
| 链路定位 | 错误最早出现阶段 |
| Wiki 已有依据 | 已调用或相关 Wiki 页面 |
| 缺失协议 | Wiki 缺少的可执行要求 |
| biz 可做事项 | 仅工程能力 |
| 建议处理 | 建议 Wiki 补充内容 |

反馈记录统一写入：

```text
docs/hegui_cli_wiki_driven_issues.md
```

## 8. 回归审查

每次调整 `hegui_cli.py` 后，至少做一次代表性案例回归。

回归时检查：

- 是否生成新输出目录。
- 风险数量是否异常大幅波动。
- 高价值风险是否稳定出现。
- 是否出现新增明显误报。
- 运行记录是否显示外部标注、Wiki 修改、Wiki 维护命令均为否。
- prompt tokens 是否接近模型上下文上限。
- 是否触达 completion 上限。

对比输出时，不只看风险数量，要看：

- 风险是否有原文证据。
- 风险是否有审查点和动作来源。
- 质量门是否反查了低风险数量、漏拆、原文纯净、证据链完整。
- 是否把“待确认”误写成确定风险。

## 9. 结构化表格与不确定性处理口径

政府采购招标文件中常见多列表格，例如评分办法、资格/符合性审查表、采购标的一览表、分项报价表、合同付款表和履约验收表。

这类表格如果在抽取后出现列错位、行合并、分值归属不清、字段缺失或上下文断裂，执行器不得在 biz 侧用硬编码业务规则修正结论。

处理原则：

- 不在 biz 中写死表格计算规则。
- 不在 biz 中硬编码具体项目、具体品类或具体风险案例。
- 不把抽取不确定的表格内容直接转成确定性风险结论。
- 当 Wiki 没有提供足够明确的表格复核协议时，作为 Wiki 驱动不足反馈。
- 需要 Wiki 明确逐项抽取、原文位置、合计或一致性复核、待确认口径和质量门反查要求后，再按协议回归运行。
